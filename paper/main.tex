\begin{abstract}
We introduce \textbf{Epi}, a domain-specific language whose type system makes the boundary between deterministic computation and LLM-inferred values explicit and enforceable at compile time. From a single \texttt{.epi} source (entities, authorization rules, AI inference steps, orchestration pipelines), the Epi transpiler emits a complete Next.js project: database schema, API routes, authorization middleware, runtime validators, LLM call wrappers, and human-review checkpoints. Every AI-inferred field carries a type-level contract (an enum, a numeric range, a confidence threshold, an optional Bayesian prior) that the transpiler discharges in the generated code. The developer does not write the validation: the type does. We argue that LLM hallucination cannot be prevented, but it can be \emph{contained}, by construction, at a type-system boundary in generated code. We exercise Epi end-to-end on the same source compiled against Anthropic Claude (cloud) and Qwen 2.5 3B (local, via Ollama): in an educational assessment task, the generated boundary intercepts a low-confidence misclassification before it reaches a database of record and routes it to teacher review. Beyond the worked example, we probe the boundary on 40 curated inputs, including adversarial ones: no value outside a declared enum ever reached the persistence path, while containment of merely \emph{wrong} values is bounded by the model's confidence calibration. Unlike typed-LLM interfaces such as BAML and DSPy, which give structure to individual model calls, Epi propagates one epistemic contract across the whole generated application, from the database column to the human-review checkpoint. A mechanized soundness proof and a controlled comparison against hand-written baselines remain future work. Epi is open-source under the Apache 2.0 license.
\end{abstract}

\section{Introduction}

Large Language Models (LLMs) are increasingly embedded in production software, performing classification, extraction, summarization, and generation alongside conventional business logic. Yet the languages we use to build that software were designed for an era of deterministic computation: a function, given the same input, returns the same output. This assumption silently fails the moment an LLM enters the call graph, because an LLM may confidently return content that is fluent but unfaithful to its input, a failure mode surveyed under the umbrella term \emph{hallucination}~\cite{ji2023}.

Throughout this paper we call a value \emph{epistemic} when it is produced by LLM inference and therefore carries uncertainty, in contrast to a \emph{rigid} value produced by ordinary deterministic code. We identify three concrete problems that arise when the two kinds of value are built in a conventional language whose type system cannot tell them apart. To make the problems concrete we phrase them against one common target, a TypeScript web application with a Prisma-managed database, but they are properties of the host language's type discipline rather than of any specific stack.

\textbf{P1: No type-level separation between rigid and epistemic values.} Consider a clinical-triage record with two fields: \texttt{status}, written by application code, and \texttt{risk}, whose value is produced by an LLM classifier. Declared in the host language as \texttt{status:~String} and \texttt{risk:~String}, the two are indistinguishable to the type checker. If the model returns \texttt{"Unknown"} instead of one of the expected labels (\texttt{"High"}, \texttt{"Medium"}, \texttt{"Low"}), the value is written to the database with no type-level alarm, because nothing in the type of \texttt{risk} records that it came from inference and must be validated.

\textbf{P2: Forced stack fragmentation.} A single AI-augmented feature typically forces the developer to hold several mental models at once. In the common stack above, that means Prisma for the database schema, TypeScript for the API, React for the UI, and a vendor SDK for the LLM call. This particular combination is only one possibility among many, but the underlying difficulty is general: one conceptual decision is distributed across several grammars and toolchains, with no single place that states the epistemic contract.

\textbf{P3: No grammar construct that requires a hallucination contract.} Output validation, retry strategies, confidence thresholding, fallback dispatch, and audit trails are the safeguards a developer would add around an LLM call. The language-design problem is that no construct in a general-purpose host grammar \emph{requires} any of them: each is an ordinary library call the developer may write, forget, or remove, and the type checker never objects. Our aim is a grammar in which these safeguards are not optional additions but obligations attached to the epistemic type itself.

Taken together, these problems motivate a language-level approach in which AI-inferred values are explicitly distinguished, constrained, validated, and audited before they can affect persistent application state.

This paper introduces \textbf{Epi}, the Epistemic Programming Interface, a domain-specific language and transpiler designed to address these problems together. At the core of Epi is an epistemic type system that separates \emph{rigid}, deterministic values from \emph{epistemic}, AI-inferred values at the type level. This distinction is not merely descriptive: whenever an epistemic value crosses into rigid application state, the generated code requires runtime validation by construction. Typed interfaces for LLMs such as BAML~\cite{baml} and DSPy~\cite{khattab2023dspy} already bring structure to a single model call, and Section~\ref{sec:related} develops in detail how Epi differs from them.

Epi also defines a compact language built from five declaration forms: \texttt{Entity} for typed schemas, \texttt{Guard} for authorization predicates, \texttt{Pulse} for AI execution units, \texttt{Pipeline} for composed flows, and \texttt{Lens} for user-interface surfaces. We do not claim this set is minimal or complete; it is the set the current transpiler lowers, and four of the five are exercised by the program of Section~\ref{sec:demonstration}. The language is specified through an EBNF grammar processed by the Lark parser toolkit~\cite{lark}, presented in Section~\ref{sec:type-system}. From this specification, the Epi transpiler generates a three-layer application architecture in which the LLM is formally excluded from the deterministic layers and may operate only within constraints emitted by them.

We demonstrate the approach through an end-to-end worked example in which the same \texttt{.epi} program runs against both a frontier cloud LLM and a small local open-weight model. The example shows that a low-confidence misclassification is intercepted as required by the type contract before it reaches persistent application state. We then exercise the same generated project on a curated set of 40 inputs to separate what the boundary guarantees structurally from what it merely mitigates. Neither is a controlled study against a hand-written baseline, which remains future work.

The central claim of this paper is intentionally limited in scope: \textbf{LLM hallucination cannot be prevented, but it can be contained by construction at a type-system boundary in generated code.}

\section{Background and Related Work}
\label{sec:related}

Epi is positioned at the intersection of three related strands of research: information-flow control, probabilistic programming, and typed or declarative tools for LLM-augmented software development.

A first point of contact is information-flow control (IFC), the discipline of tracking how values in distinct domains, classically \emph{public} and \emph{secret}, may propagate through a program, and of rejecting programs that leak one into the other. Sabelfeld and Myers~\cite{sabelfeld2003} survey the language-based form of this discipline, in which the type system itself enforces a \emph{non-interference} property: the observable outputs of a program must not depend on its secret inputs. The Rigid/Epistemic distinction in Epi is structurally analogous, with \emph{epistemic provenance} taking the place of confidentiality. Russo and Sabelfeld~\cite{russo2010}, for example, contrast dynamic and static flow-sensitive analyses that encode forms of non-interference between value domains. Epi adapts this general discipline to \emph{epistemic provenance} (whether a value originated from deterministic code or from probabilistic inference) rather than to confidentiality levels. The transpiler enforces non-interference by emitting validation at every domain crossing.

A second related tradition is probabilistic programming. Languages such as ProbZelus~\cite{baudart2020} and SlicStan~\cite{gorinova2019} provide explicit constructs for representing probabilistic computation, often treating distributions as first-class elements and distinguishing deterministic computation from probabilistic inference. Epi shares with this literature the concern that uncertainty should be represented explicitly in the language rather than hidden inside ordinary values. However, its goal is different: rather than specifying models or compiling inference procedures, Epi operates at the level of LLM-augmented software systems, orchestrating calls to pre-trained model endpoints rather than implementing inference algorithms.

Epi also relates to recent work on typed interfaces for LLMs and declarative AI programming. BAML~\cite{baml} provides typed signatures for LLM functions, while DSPy~\cite{khattab2023dspy} compiles declarative signatures into optimized prompting strategies. These systems make important contributions by giving more structure to interactions with language models, but they typically operate at the level of individual LLM calls or prompt modules. Epi extends this idea to the level of whole-application generation: rather than typing only a model invocation, Epi uses a single source specification to generate database structures, middleware, validators, and user-interface scaffolding. In this respect, it also connects to full-stack domain-specific languages such as Wasp~\cite{wasp}, which targets React and Node applications from a high-level specification but does not encode a type-level distinction for AI-inferred values. What separates Epi from all three is the epistemic type discipline itself: audit-by-construction is a property of the type, not a feature the developer can forget to add.

\section{The Epistemic Type System}
\label{sec:type-system}

In Epi, every value belongs to one of two epistemic domains in the type system: \emph{Rigid} or \emph{Epistemic}.

\textbf{Rigid types} are deterministic and have no AI involvement:
\begin{center}
\texttt{UUID \quad Text \quad Int \quad Float \quad Decimal \quad Bool \quad DateTime \quad JSON}
\end{center}

\textbf{Epistemic types} are AI-inferred and carry mandatory validation parameters: \texttt{AI.Enum}, \texttt{AI.Text}, \texttt{AI.Classification}, \texttt{AI.Score}, and \texttt{AI.Embedding}, each parameterized by its specific constraints (allowed values, max tokens, dimensions, etc.) plus optional cross-cutting attributes such as \texttt{strict}, \texttt{prior}, and \texttt{confidence\_\allowbreak{}threshold}.

The two domains are also syntactically distinct in the grammar, and each declaration form of Section~\ref{sec:primitives} has its own production. Writing \texttt{ID} for identifiers and eliding the lexical productions, the core of the EBNF is:

\begin{verbatim}
decl ::= entity_decl | guard_decl
  | pulse_decl | pipeline_decl | lens_decl
entity_decl ::= "Entity" ID "{" field+ "}"
field ::= ID ":" type
type ::= rigid_type | epistemic_type
rigid_type ::= "UUID" | "Text" | "Int"
  | "Float" | "Decimal" | "Bool"
  | "DateTime" | "JSON"
epistemic_type ::=
    "AI.Enum" "(" enum_args ")"
  | "AI.Text" "(" text_args ")"
  | "AI.Score" "(" score_args ")"
  | "AI.Classification" "(" cls_args ")"
  | "AI.Embedding" "(" emb_args ")"
enum_args ::= id_list ("," enum_attr)*
enum_attr ::= "strict" ":" bool
  | "prior" ":" distribution
  | "confidence_threshold" ":" number
guard_decl ::= "Guard" ID "{" cond "}"
pulse_decl ::= "Pulse" ID pulse_body
pulse_body ::= "{" input protect?
  (process | trace_decl+) output "}"
trace_decl ::= "Trace" ID trace_body
trace_body ::= "{" execute
  expose? checkpoint? "}"
pipeline_decl ::= "Pipeline" ID
  "{" flow on_error? "}"
lens_decl ::= "Lens" ID "{" lens_body "}"
\end{verbatim}

The epistemic domain is therefore not a convention but a syntactic category: no production allows an \texttt{AI.*} constructor where a \texttt{rigid\_type} is expected, or the reverse, so the distinction survives parsing and reaches the generator as a tag on the node rather than as a naming discipline.

A field declared with an epistemic type imposes obligations on the generated code:

\begin{verbatim}
risk: AI.Enum(High, Medium, Low,
              strict: true,
              confidence_threshold: 0.85)
\end{verbatim}

Here \texttt{High}, \texttt{Medium}, and \texttt{Low} are the only admissible labels; \texttt{strict}
forbids any value outside that set; and \texttt{confidence\_\allowbreak{}threshold} is the minimum
self-reported confidence below which the value is not persisted but routed to human
review. A second epistemic type, \texttt{AI.Score}, applies the same discipline to numeric
inference: \texttt{AI.Score(min: 0, max: 5)} bounds the model to a numeric range
rather than an enumeration, and the transpiler emits the matching bound check. In both cases the declaration is a
\emph{contract}, not a hint.

The single \texttt{risk} declaration above requires the transpiler
to emit, in the output project, four artifacts:
\begin{description}
  \item[(a)] A \textbf{database column} of compatible storage type.
  \item[(b)] A \textbf{runtime validator}, emitted as a Zod~\cite{zod} schema in the TypeScript output. Zod is a schema-declaration library whose objects parse an incoming value at runtime and raise an error when it falls outside the declared shape; here the generated schema rejects any value outside the declared enum.
  \item[(c)] An \textbf{LLM inference call} wrapped to return JSON containing the value and a \texttt{\_confidence} field in $[0,1]$. The field is \emph{elicited}: the transpiler appends an instruction to the system prompt requiring the model to report it, rather than deriving it from token log-probabilities, which providers do not expose uniformly. When the model omits it, the generated code substitutes 0.5, below every threshold declared here, so an absent confidence fails towards review.
  \item[(d)] A \textbf{confidence-aware dispatch}: if reported confidence is below the threshold, route to a Checkpoint endpoint for human review; otherwise validate and persist.
\end{description}

None of these artifacts is optional: a type-correct Epi program cannot omit any of them, because the type itself forces their emission. This is the central design choice: the \emph{type carries an obligation that the transpiler discharges in the generated code}. In Pierce's terms~\cite{pierce2002}, the transpiler refuses to emit programs that persist unvalidated AI output. The invariant we maintain informally is the following: for every well-typed Epi program, every path from an \texttt{AI.*}-typed expression to a persistence sink in the generated code passes through a validator on that type. Section~\ref{sec:discussion} discusses why we describe this invariant as informal in the current stage.

Crucially, the typed-signature DSLs discussed in Section~\ref{sec:related} generate only artifact~(c) above; Epi additionally generates (a), (b), and (d) as structural consequences of the same declaration.

These obligations are stated for \texttt{AI.Enum}, the strongest of the epistemic types; the others follow the same pattern with weaker guarantees. \texttt{AI.Classification} constrains a declared label set but admits more than one label per inference, \texttt{AI.Embedding} fixes the dimension of the emitted vector, and \texttt{AI.Text} bounds only length and format, because free-form generation admits no enumeration of admissible values. Containment therefore degrades with the type rather than uniformly: what the boundary can reject is exactly what the type constrains, so an \texttt{AI.Text} field still obtains (a), (c), and (d), including the review path, but its validator has no membership test to perform. This is a limit of the discipline, not an oversight of the implementation, and it is why the evaluation below uses an enumerated field.

\subsection{The Five Primitives}
\label{sec:primitives}

Epi programs are composed of five main primitives: \textbf{Entity} declarations, which define typed schemas; \textbf{Guard} declarations, which specify authorization predicates over the request context; \textbf{Pulse} declarations, which represent AI execution units configured with prompt files, temperature settings, and fallback strategies; \textbf{Pipeline} declarations, which compose Pulse flows with explicit error policies; and \textbf{Lens} declarations, which describe user-interface surfaces. Among these primitives, only Pulse and the epistemic fields within Entity invoke the AI, while the remaining constructs are deterministic. This design reinforces the separation between conventional computation and probabilistic inference within the language.

A Pulse may also be decomposed into a sequence of \emph{Trace} steps. Each Trace can \texttt{Expose} intermediate reasoning fields and pause execution at a \texttt{Checkpoint} for human review before the next step proceeds. The following Pulse illustrates the constructs together:

\begin{verbatim}
Pulse TriageNote {
  Input:   Record
  Protect: Guard.CliniciansOnly
  Trace Interpret {
    Execute: AI.reason(
      source: Input.note,
      prompt: file("interpret.md"))
    Expose:     findings, severity
    Checkpoint: ReviewRequired(
      role: "Clinician")
  }
  Output: Record.risk
}
\end{verbatim}

Informally, the Pulse executes as follows. \texttt{Protect} discharges the named Guard before any inference runs, so an unauthenticated request never reaches the model. The \texttt{Interpret} Trace then issues one AI call and binds the fields listed in \texttt{Expose} from the model's JSON output. Because the Trace declares a \texttt{Checkpoint}, execution suspends and the exposed fields are surfaced through a generated inspect/resume HTTP endpoint; the step resumes only after a user in the \texttt{"Clinician"} role approves or corrects them. Each paused step carries the exposed fields, the raw model output, the reported confidence, the threshold that caused the pause, the reviewer's identity, and any correction injected into the next step, so the record an audit needs is produced by the generated code rather than added to it. The emitted store holds that record behind a save/get/update interface backed by an in-process map; binding it to a durable backend is a deployment concern the interface isolates, and the current release leaves it undone. The value finally written to \texttt{Record.risk} is thus the \texttt{AI.Enum} declared earlier, now guaranteed to be validated and, when uncertain, reviewed. This mechanism is intended for high-stakes workflows, such as educational assessment, clinical pre-screening, and legal triage, where it is not sufficient to audit only the final output: the reasoning process itself must also be inspectable.

An \texttt{AI.Enum} field may additionally declare a prior distribution over its labels, in which case the transpiler emits a Bayesian-update function that combines the prior with the model's reported likelihoods via Bayes' rule, so that the posterior couples model output with domain base rates rather than overwriting them. Since both attributes may be declared on the same field, the composition order should be stated: in the current implementation the two do not compose. The dispatch of artifact~(d) compares the raw reported confidence against \texttt{confidence\_\allowbreak{}threshold}, while the Bayesian function sits next to the validator and exposes a posterior of its own. Comparing the threshold against that posterior, so that a label the prior deems rare must clear a higher bar, is the natural composition and is left to future work.

We now describe how a Lark/EBNF grammar and these typing constraints become a runnable Next.js project.

\section{Transpiler Architecture}

The Epi transpiler is organized into three layers. The first layer parses the \texttt{.epi} source with the Lark grammar into an abstract syntax tree in which every type node carries a domain tag, \emph{rigid} or \emph{epistemic}, assigned by the production that built it: the tag is not inferred by a later analysis, because the grammar of Section~\ref{sec:type-system} already separates the two categories. An \texttt{Entity} node therefore exposes its fields under two derived views, one per domain, and the tag is the pivot of the whole design, since generator dispatch is a case split on it. The second layer, the \emph{Rigid Generator}, consumes the rigid view and emits the Prisma schema, the Next.js route handlers, the authorization middleware derived from \texttt{Guard} conditions, and the Zod validators. The third layer, the \emph{Epistemic Generator}, consumes the epistemic view and emits the LLM call wrapper, the confidence extraction and threshold comparison, the Bayesian update function when a prior is declared, and, for a Pulse decomposed into Traces, a trace store together with an \texttt{inspect} and a \texttt{resume} HTTP endpoint per Trace.

Splitting the generators by epistemic domain rather than by output artifact is what carries the invariant. The conventional organization of a full-stack generator is one module per target file; under that split, the validator of an AI-inferred field is emitted by the schema module under a conditional and the confidence-aware dispatch by the route module under another, so nothing structural prevents a later code path from lowering an epistemic field while skipping one of them. Making the domain the dispatch key removes that possibility: an epistemic node has exactly one lowering, and that lowering emits the validator and the dispatch together with the call. The four artifacts of Section~\ref{sec:type-system} are thus produced by a single traversal rather than left to the developer, and a single \texttt{.epi} source replaces the several grammars identified in P2, consolidating database, API, interface, and LLM-related logic within one declarative specification.

A central design principle of this architecture is that the LLM is formally excluded from Layers~1 and~2. The deterministic layer defines and encodes the constraints under which the application operates, while the epistemic layer can only act within those constraints. This separation is intentionally similar to the distinction between \emph{standard library} and \emph{user code} in mainstream type-system implementations: the constraints are not runtime checks added after the fact, but compile-time invariants that the generated runtime cannot violate without failing closed.

Layer~3 also emits a provider-agnostic LLM client, implemented as a single \texttt{lib/llm-client.ts} file, which abstracts the model provider behind a uniform \texttt{llmCall(params)} interface. Runtime environment variables (including \texttt{EPI\_AI\_PROVIDER}, \texttt{EPI\_AI\_MODEL}, and \texttt{EPI\_AI\_BASE\_URL}) select between Anthropic Claude~\cite{anthropic} and any OpenAI-compatible endpoint, with Ollama~\cite{ollama} targeted for local open-weight models. Across these providers, the epistemic contract remains the same: the model output must be valid JSON, include a \texttt{\_confidence} field, and be parseable by the corresponding Zod schema. In this architecture, the choice of provider is therefore treated as a deployment concern rather than a code-level change.

\section{Demonstration}
\label{sec:demonstration}

We exercise the system end-to-end on a single educational scenario, presented as a worked example rather than a controlled study.

The complete \texttt{.epi} source is reproduced below in full, with identifiers rendered in English; the program distributed with the artifact is identical except that its identifiers and its prompt are in Portuguese.

\begin{verbatim}
Entity Submission {
  id:     UUID(auto),
  prompt: Text,
  answer: Text,
  evaluation: AI.Enum(
    Correct, Partial, Incorrect,
    strict: true,
    prior: Distribution(Correct: 0.40,
      Partial: 0.45, Incorrect: 0.15),
    confidence_threshold: 0.85)
}

Guard TeachersOnly {
  Condition: Auth.Role == "Teacher"
}

Pulse EvaluateAnswer {
  Input:   Submission
  Protect: Guard.TeachersOnly
  Process:
    Execute: AI.classify(
      source: Input.answer,
      prompt: file("evaluate.md"),
      temperature: 0.1,
      on_low_confidence:
        Checkpoint.ReviewRequired(
          role: "Teacher"),
      on_fail:
        Fallback.ManualReview(
          Queue: "Teachers"))
  Output: Submission.evaluation
}

Pipeline AssessmentFlow {
  Flow: EvaluateAnswer
  On_Error: Retry(max: 2,
                  backoff: exponential)
}
\end{verbatim}

The single epistemic field \texttt{evaluation} declares a prior over its labels and a confidence threshold; the Pulse routes low-confidence outputs to a teacher checkpoint and malformed outputs to a manual-review queue. From this source the transpiler emits 13 files totalling 477 lines, of which 287 are TypeScript and Prisma schema; the remainder is project configuration, the extracted prompt, and a README.

We compile the same \texttt{.epi} source twice and run both deployments unchanged: (a) against \textbf{Anthropic Claude Sonnet~4} in the cloud; (b) against \textbf{Qwen~2.5 3B Instruct} (Q4\_K\_M, $\sim$1.9~GB) served locally by Ollama on consumer hardware (Apple Silicon, 16~GB RAM). The only difference is the value of \texttt{EPI\_AI\_PROVIDER} in the deployment's \texttt{.env} file. Each deployment receives the same four inputs against the prompt ``What is photosynthesis?''. In this case, the small model misclassified a textbook-correct answer as \texttt{"Partial"}, producing a false negative that, if persisted, would have unfairly penalized the student. However, the model's own reported confidence, 0.8, fell below the threshold declared in the type definition, set at 0.85. As a result, the dispatch logic emitted by the transpiler routed the case to a human reviewer \emph{before} it reached the database. The developer did not write any specific code for this behavior. Instead, it follows from the single type annotation \texttt{confidence\_threshold:~0.85}, which the transpiler discharges in Layer~3, together with the Checkpoint dispatch and the audit trail, none of which the developer had to write.

The same three real inputs were also submitted to Anthropic Claude Sonnet~4. In that setting, the textbook-correct answer was classified as \texttt{"Correct"} with confidence above 0.9 and therefore passed validation directly. The pipeline thus behaves identically at the boundary across both providers, even though absolute accuracy and latency differ. This result supports the claim that the epistemic contract is enforced independently of the inference engine used at deployment time.

The fourth row of Table~\ref{tab:evaluation} exercises the schema-validation path through a deliberately malformed JSON response. In this case, the Zod schema rejects the value, and the transpiler-emitted \texttt{Fallback.\allowbreak ManualReview} mechanism routes the request to a manual review queue. Again, no handwritten error path is required. This example illustrates the central containment claim of Epi: hallucination or malformed model output is not prevented at the source, but it is prevented from silently crossing the type-system boundary into persistent application state.

\subsection{Containment on a Curated Input Set}
\label{sec:containment}

A single scenario shows that the boundary can fire, not how often it fires when it should. We therefore exercised the same generated project on a curated set of 40 inputs, each carrying a gold label and a written justification for that label. The set is deliberately unbalanced towards cases where the boundary should be tested rather than confirmed: alongside complete and clearly wrong answers, it contains answers that are right but incomplete, answers that are fluent yet wrong on a single word, inputs with no defensible single label, and adversarial inputs that attempt to force a label outside the declared enum. The items are written in Portuguese, matching the distributed program noted above.

The measurement harness does not reimplement the boundary. It imports the transpiler-emitted Pulse and records what that function returned, so the threshold comparison, the schema validation and the dispatch to Checkpoint or Fallback all execute in generated code. Inference ran against Qwen~2.5 3B served locally, three times per item at temperature~0.1, with the item-level outcome taken as the majority across repeats; 2 of the 40 items changed outcome between repeats. Median latency was 621~ms. Results appear in Table~\ref{tab:containment}.

Two results follow, and they carry different weight. The first is structural and does not consult the gold labels at all: across every run, no value outside the declared enum reached the persistence path. This was not for lack of attempt. Repeating the same set against a deliberately weaker model, Llama~3.2 1B, one adversarial item drove the model to emit the invented label \texttt{CORRET\'ISSIMO} on all three repeats, and the generated Zod validator rejected it and routed the case to the manual-review queue; a second item drove it to emit unparseable output on all three repeats, caught by the parse path of the same Fallback. Neither path was written by hand, and neither depends on the inference engine behaving well.

The second result is weaker and depends on the gold labels. Of the 30 items carrying a single defensible label, the model's own output would have written a wrong value 12 times had it gone to the database directly. The boundary kept 6 of those 12 out, at the cost of sending half of all items to human review. Containment here is therefore partial, and it is bounded by something the type system does not supply: the model's self-reported confidence must actually track its errors. The 1B model illustrates the bound by violating it. It reports high confidence almost everywhere, so it escaped with all 18 of its wrong values while sending only 22\% of items to review.

The two columns of Table~\ref{tab:containment} isolate a language-level effect. They differ in one token of the \texttt{.epi} source: whether the AI call declares \texttt{source:\ Input.answer} or \texttt{source:\ Input}, that is, whether the model receives the answer alone or the answer together with the question it responds to. The epistemic contract is unchanged. Yet under-specifying the source both doubles the model's raw error rate and defeats the boundary on the errors that remain, because a verdict formed without the necessary information is still reported confidently. This suggests that source adequacy belongs in the contract next to the threshold, and it is a concrete instance of the calibration question discussed in Section~\ref{sec:discussion}.

Three limitations bound these numbers. The items are synthetic and were authored for this evaluation rather than collected, so they probe the boundary rather than estimate a rate in the field. The gold labels were written by a single annotator, with no independent second pass and therefore no inter-rater agreement figure; the structural result above is unaffected by this, since it never consults a label. Finally, containment is not accuracy: three adversarial items that hijack the classification produced a wrong but confidently reported in-domain label, which the boundary passed. A type system can require that an uncertain value be reviewed, and can guarantee that an out-of-domain value is never written, but it cannot detect a confident and well-formed lie.

\section{Discussion and Limitations}
\label{sec:discussion}

The current specification of Epi's type system is implementation-oriented rather than fully mechanized. The paper presents a working transpiler and an empirical demonstration, but does not yet provide a mechanized soundness proof. The invariant described in Section~\ref{sec:type-system}, namely that every path from an \texttt{AI.*}-typed expression to a persistence sink must pass through a validator for that type, can be understood as a non-interference property between rigid and epistemic value spaces. A full formal treatment, for example in a proof assistant such as Coq~\cite{bertot2004} or Agda~\cite{norell2009}, would require the definition of typing judgments, operational semantics, and a soundness theorem, and is left as future work.

A second open question concerns how the \texttt{confidence\_\allowbreak{}threshold} is chosen. In the current design it is a developer-supplied constant: the value below which an inferred result is treated as too uncertain to persist without review. This places the calibration burden on the developer, and a fixed constant ignores that the quantity being compared is a confidence the model reports about itself, elicited by prompt as described in Section~\ref{sec:type-system} and not guaranteed to track the model's actual error rate. Section~\ref{sec:containment} shows the consequence directly: the same boundary that contained half of one model's errors contained none of a weaker model's, because that model reported high confidence almost everywhere. We see three more principled routes, which we leave to future work: deriving the threshold from a labelled validation set so that it targets a chosen precision on human-reviewed cases; comparing it against the Bayesian posterior rather than the raw report, which also resolves the composition order left open in Section~\ref{sec:type-system}, so that a label the \texttt{prior} deems rare must clear a higher bar; and recalibrating reported confidences before comparison. In all three, the language surface would be unchanged, since the threshold is already a first-class attribute of the epistemic type; only the value bound to it would be computed rather than written by hand.

The current implementation also has limitations in terms of target coverage. At present, the transpiler emits a complete Next.js project, while a FastAPI target is only partially implemented and remains gated in the CLI until the implementation is complete. This limitation is therefore an engineering constraint of the current prototype rather than an essential property of the language design.

Finally, the Lens primitive includes a \texttt{Mood} declaration that currently maps keywords to UI utility classes through a deterministic lookup table. This mechanism is the weakest element of the present design, because its connection to the epistemic type discipline is less central than that of Entity, Pulse, Trace, or Checkpoint. For this reason, it is marked as experimental in the documentation.

\section{Conclusion and Future Work}

LLM hallucination is a property of the underlying inference, not of the surrounding code; it cannot be prevented at the type-system level. It can, however, be \emph{contained}. A type discipline that distinguishes deterministic from epistemic provenance can require, by construction in generated code, that every AI-inferred value pass a validator, report its confidence, and surface for human review when uncertain. We have implemented this discipline as a language and a transpiler, exercised it end-to-end against a frontier cloud model and a small local open-weight model, and shown both that the boundary catches a misclassification that would otherwise reach a database of record and that it holds identically across two very different inference engines. Where BAML and DSPy make a single model call well-typed, Epi takes the crossing from inference into persistent state as the thing to be typed, which is why one declaration reaches the schema, the validator, and the review path at once. Three directions follow: a mechanized formalization of the type system, a controlled comparison against hand-written baselines on correctness and audit coverage, and a \texttt{confidence\_\allowbreak{}threshold} that is computed, from a labelled validation set or from the declared \texttt{prior}, rather than written by hand.
